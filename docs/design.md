# 設計

MVP（[mvp.md](mvp.md)）で実現したい動作を実現するための、現時点での設計。本書が設計内容の単一記載場所であり、更新は常にここへ行う。

**注記**: 土台として挙げる実績OSSの選定は会話で合意済みだが、自作部分（①〜③＋検証器）の設計内容はまだエージェントの案であり、確定はユーザーの承認を待つ。

## 仮想液タブ 機器仕様（案・承認待ち）

仮想液タブは「スクリプトの集合」ではなく、**実物の液タブと同じ存在論を持つ周辺機器（製品）1台**として扱う。以下はユーザー発言から導出した機器要件であり、全構成決定の採点基準とする（Windows等のOS既定挙動は基準ではなく各候補の内部事情）。

| # | 要件 | 内容 |
|---|---|---|
| R1 | 単一ユニット性 | 画面＋ペン＋両者の関連付けが「1台ぶん」の管理単位。起動＝組み立て、終了＝解体 |
| R2 | 物理からの隔離（双方向） | 物理USB機器の有無やOSの実機デジタイザ向け規則（ContainerID・内蔵判定・ペンキャリブレーション等）に挙動を左右されない。メインディスプレイ（視聴環境）を一切侵さず、逆にメインへも漏れない |
| R3 | 起動・終了 | ユニット単位で接続・切断できる。終了時の残留ゼロ（押しっぱなしペン・ゾンビデバイス・レジストリ残骸・白画面占有・OS設定変更はすべて残留物） |
| R4 | 増設 | 同じ手順で2台目以降を生やせる |
| R5 | 識別とルーティングの所有 | 「このペンタブはこの画面のやつ」という対応を**本システムの設定値として明示的に**持つ。OSデフォルトと奪い合うものではない |
| R6 | 入力のリアルさとIF再利用 | 入力は可能な限り本物の液タブ（筆圧等を保持）。IFは仮想液タブ→仮想〇〇へ使い回せる共通設計。「IFは神＝既存の詳しいIFを使え、神が悪ければ更好的IFを考案して殴れ」 |
| R7 | 検証規律 | 成功宣言は証拠（キャプチャ・ログ）確認後のみ |

## アーキテクチャ（構成検討中: 2026-09-23 時点の正直な状態）

```
脳（AIエージェント）
──────────────────────────────────────
① セッション層   クリスタの起動・終了・画面状態の管理
② 盤面層         ドキュメント座標系＋フレームバッファ読み取り＋キャリブレーション
③ 筆層           ストローク定義 → サンプル列コンパイラ → ペン配送（構成は上記評価表で検討中）
④ 土台           仮想モニタ(VDD) / 仮想ペン(vmulti) / 配送経路の候補は評価表参照
```

- 第一回検証（電卓7×6=42、キャプチャ4枚、メイン無干渉、b28ece8）は **(iv) ISPI** で成立しており、「読み→書き→読み」の循環自体は実証済み
- 筆層の確定構成は評価表の承認後に決める（旧「vmulti→OTD→クリスタ確定」表記は #6/#7 の経過と矛盾するため撤去した）

### 入出力の原理

- **読み**: 仮想モニタのフレームバッファをキャプチャし、盤面（キャンバスの現在状態）をピクセル単位で取得する。書き込みと同一の座標系であるため、座標ズレのない盤面になる。座標系は物理ピクセルに統一（Per-Monitor DPI Aware。実験事項#8参照）
- **書き**: ペン配送経路は上記評価表で承認待ち。第一回検証の実績（ISPI）ではデスクトップ絶対座標直指定で仮想モニタ内のアプリを操作できたが、機器要件R1〜R5を満たす本体構成ではない。UI操作・文字入力の標準キーボード注入は経路に依存しない
- **外部エージェント基盤への非依存**: ComputerUse等の既存の画面操作基盤は本システムの構成要素としない

## 設計方針

- **脳と手足の分離**: 判断・意図はすべてエージェント（脳）が担う。プログラム（手足）は機械的に忠実であることを良しとする。人間らしさ等の創作的性質はプログラムに固定せず、その都度エージェントが入力として与える
- **読みと書きの同一座標系**: フレームバッファ（読み）とペン注入（書き）が同じ座標空間に乗る
- **実績部品の組み合わせ**: 仮想ペン・仮想モニタ・タブレットドライバは実績のあるOSS（vmulti / VirtualDisplayDriver / OpenTabletDriver）を正規の使い方で利用する。その他は自作する（自作範囲は「自作システム」の節のみに記載し、本書の他箇所では列挙しない）
- **バージョン固定運用**: 依存OSSは動作確認したバージョンに固定し、勝手な更新で壊れないようにする

### 土台（実績部品）

| 部品 | 役割 | 状態 |
|---|---|---|
| OpenTabletDriver（OTD） | ペン配送候補(i)の中核。vmultiを入力タブレットとして検出させ、OTDの画面マッピング設定（＝各社液タブドライバと同じルーティングIF）で出力先ディスプレイを指定する。Windows Ink出力で筆圧保持（要: VMultiドライバ＋Windows Inkプラグイン） | 評価表(i)として本格実験待ち（承認後） |
| vmulti（X9VoiD/vmulti-bin） | 仮想HIDデジタイザ。OTD検出用の入力装置として使う。単一インスタンス固定（R4増設は構成課題） | 確定（入力装置として。旧「OSへの直書き」経路は実験事項#7で不合格） |
| VirtualDisplayDriver（VirtualDrivers） | 仮想モニタ。液タブの「画面」役。盤面の座標系を提供し、フレームバッファを読み取り可能にする | 確定 |

### 自作システム（自作範囲はここにのみ記載する）

| 層 | 役割 | 状態 |
|---|---|---|
| ① セッション層 | クリスタの起動・終了・画面状態の判定・遷移・ダイアログ処理。筆を撃つ前に「正規のキャンバス状態」を用意する。UI操作はペンクリック（OTD経由）とキーボード注入、状態判定はフレームバッファとウィンドウ情報による。**加えてセッション開始時に仮想モニタの状態確認と表示トポロジの拡張設定（OS標準API SetDisplayConfig）を行い、プライマリモニタが物理モニタであることを保証する**（VDDControlにトポロジ設定は存在しないためOS側で設定するのはセッション層の責務。再起動時に仮想モニタがメインモニタ化する既知事故 VDD Issue #31 への対策） | 設計中 |
| ② 盤面層 | ドキュメント座標系の定義、仮想モニタのフレームバッファ読み取り、キャリブレーション | 設計中 |
| ③ 筆層（ストロークコンパイラ） | ストローク定義（中間表現）を受け取り、位置・筆圧・時刻つきのサンプル列（毎秒約200回）に展開し、vmultiへ書き込む。設計要件: どのような状況でもストロークを必ず終端させ、ペンが押しっぱなしのまま残る状態を作らない | 設計中 |
| ペンイベント検証器（受信ロガー） | 筆層の出力する報告列が正しい形かを、クリスタに通す前に検証する | 設計中 |

- 実装言語: C#（Windows内蔵コンパイラ csc でビルド可能。OTDのタブレット定義JSON・報告形式の参考実装もC#で存在するため）
